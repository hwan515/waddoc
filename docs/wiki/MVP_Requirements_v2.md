# 도서·산간 방문형 비대면 진료 서비스 — MVP 요구사항 계획서 v2

## 1. 문서 목적

본 문서는 도서·산간 의료취약지 비대면 진료 서비스의 MVP 범위, 시나리오, 기능/비기능 요구사항, 일정 및 리스크를 정의한다.

- MVP 범위를 명확히 고정한다.
- 데모 기준에서 반드시 동작해야 하는 핵심 흐름을 정의한다.
- 개발, 기획, 운영이 같은 기준으로 의사결정할 수 있게 한다.
- ERD, API, 화면 설계, Jira 분해의 상위 기준 문서로 사용한다.

### v1 → v2 주요 변경사항

| 항목 | v1 | v2 |
|------|----|----|
| 전화 채널 | 구현 방식 미정 | **웹 전화 시뮬레이터** (React 기반) |
| 본인확인 | "신분증 + 카메라" (불명확) | **사전 등록 사진 + 카메라 촬영 사진 비교** (IDV AI) |
| 보호자 MVP 범위 | 포함/제외 모순 | **읽기 전용만 MVP** (3자 WebRTC는 P1) |
| 예약 변경 | 포함/제외 모순 | **MVP 제외** (P1). 조회·취소만 P0 |
| 바이탈 | 실측 전제 | **더미 데이터 전송** (실기기 연동 없음) |
| 처방/후속예약 | P0/P1 불명확 | **기록만 P0**, 실제 생성/연계는 P1 |
| 상태 enum | 미정의 | 주요 엔티티별 상태 정의 포함 |
| 프론트엔드 | 미명시 | React 명시 |

## 2. 프로젝트 개요

의료취약지 환자가 **앱 설치 없이 웹 전화 시뮬레이터**로 진료를 예약하고, 이후 의사와 원격 화상진료를 진행할 수 있도록 지원하는 서비스다.

MVP 핵심 흐름:

**웹 전화 시뮬레이터 진입 → 환자 식별 → 증상 인테이크(STT) → 진료과/의사 추천 → 예약 생성 → 케이스 생성 → 미션/출동 관리 → 차량 태블릿 진료 시작 → 사전 등록 사진 기반 본인확인 → 확인 → 진료 세션 참가(WebRTC) → 진료 요약/처방 여부 기록 → 감사 로그**

예약, 진료 준비, 실제 진료, 운영 추적은 서로 다른 라이프사이클을 가지므로, **BOOKING**, **CARE_CASE**, **MISSION**, **CONSULTATION_SESSION**을 분리한다.

## 3. MVP 목표

### 3.1 비즈니스 목표

- 의료취약지 환자가 웹 전화 시뮬레이터로 예약을 완료할 수 있어야 한다.
- 환자와 의사가 원격 진료에 실제로 참여할 수 있어야 한다.
- 운영자가 예약부터 진료 종료까지 상태를 추적할 수 있어야 한다.

### 3.2 제품 목표

- 웹 전화 시뮬레이터 기반 신규 예약, 예약 조회, 예약 취소
- 증상 입력 및 1차 분류
- 의사 또는 진료과 추천
- 케이스 및 운영 단위 생성
- 1:1 화상진료 (의사-환자)
- 보호자 로그인 및 진료 요약 조회 (읽기 전용)
- 로그인, 접근 권한, 세션, 감사 로그 관리

### 3.3 데모 성공 기준

1. 신규 예약 시나리오가 처음부터 끝까지 끊기지 않고 동작한다.
2. 기존 예약 조회/취소가 동작한다.
3. 사전 등록 사진 기반 본인확인이 동작한다.
4. 1:1 WebRTC 화상진료가 동작한다.
5. 예외 상황에서도 시스템이 죽지 않고 복구 멘트 또는 대체 경로를 제공한다.
6. 운영자가 예약·케이스·세션 상태를 확인할 수 있다.
7. 보호자가 로그인하여 진료 요약을 조회할 수 있다.

## 4. 프로젝트 범위

### 4.1 MVP 포함 범위

- 웹 전화 시뮬레이터 기반 진입 (React)
- 생년월일 6자리 + 발신번호 기반 환자 식별
- 인테이크 세션 관리
- 증상 입력(STT) 및 분류
- 진료과 / 의사 추천
- 예약 생성, 조회, 취소
- 케이스 생성
- 미션/운영 상태 관리
- 의사 / 관리자 / 보호자 웹 로그인
- Access Token(메모리) + Refresh Token(HttpOnly 쿠키) 인증
- 사전 등록 사진 + 카메라 기반 본인확인 (IDV AI)
- 바이탈 더미 데이터 입력 및 표시
- 1:1 화상진료 세션 생성 및 참여 (LiveKit WebRTC + TURN)
- 진료 요약, 처방 여부, 재진 필요 여부 기록
- 보호자 로그인 및 진료 요약 조회 (읽기 전용)
- 알림 발송
- 감사 로그

### 4.2 MVP 제외 범위

- 실제 전화망(PSTN) 연동
- **예약 변경** (슬롯 반환/재점유, 동시성 처리 비용이 높으므로 P1)
- 첫 방문 현장 얼굴 촬영 후 관리자 승인 기반 기준 사진 등록
- **신분증 OCR + 신분증 얼굴 비교 + 사전 등록 사진 3자 대조 기반 확장형 본인확인** (P1 선택)
- 동의 UI 및 동의 기록
- 보호자 실시간 3자 WebRTC 진료 참여
- 보호자 접근 권한 세밀 관리 (GUARDIAN_INVITE, GUARDIAN_ACCESS_GRANT)
- 실제 바이탈 기기 연동 (MVP는 더미 데이터)
- 후속 예약 실제 생성 (MVP는 재진 필요 여부 기록만)
- 처방 시스템 연계/고도화 처방 관리 (MVP는 처방 여부 기록만)
- 고도화된 AI 진단
- 소셜 로그인
- 정식 EMR 완전 통합
- 자동 배차 최적화 고도화
- 고급 분석 대시보드

## 5. 사용자 정의

### 5.1 환자
- 웹 전화 시뮬레이터로 서비스에 진입한다.
- 신규 예약, 기존 예약 조회, 예약 취소를 수행할 수 있다.
- 본인확인은 사전 등록된 얼굴 사진과 실시간 카메라 촬영으로 수행한다.

### 5.2 보호자 (MVP: 읽기 전용)
- 웹페이지에 로그인한다.
- 본인에게 연결된 환자의 진료 요약 내용을 확인할 수 있다.
- **MVP에서는 실시간 WebRTC 진료 참여 불가** (P1 확장).

### 5.3 의사
- 웹페이지에 로그인한다.
- 자신에게 배정된 예약, 케이스, 세션에 접근한다.
- 진료 시작, 종료, 요약 입력, 처방 여부/재진 필요 여부 기록이 가능하다.
- **후속 예약 실제 생성은 P1.**

### 5.4 관리자
- 웹페이지에 로그인한다.
- 환자, 예약, 케이스, 미션, 세션, 알림, 예외 상태를 관리한다.

## 6. MVP 핵심 시나리오

### 6.1 시나리오 개요

환자가 **웹 전화 시뮬레이터**로 신규 예약을 생성하거나 기존 예약을 조회·취소하고, 예약된 차량이 출동하여 환자를 탑승시킨 뒤, 차량 태블릿에서 **진료 시작**을 누르고 **사전 등록 사진 기반 본인확인** 및 확인 절차를 거쳐 1:1 WebRTC 비대면 진료에 참가한다.

---

### 6.2 환자 전화 진입 및 예약 시나리오

#### 전화 시뮬레이터 기술 구현

| 항목 | 구현 방식 |
|------|-----------|
| 전화 진입 | React 웹 전화 시뮬레이터 UI |
| 메뉴 버튼 입력 | 화면 다이얼 패드 버튼 클릭 후 다음 API 직접 호출 |
| TTS 송출 | Web Speech API 또는 서버 TTS 음성 파일 재생 |
| 음성 입력(STT) | 브라우저 음성 입력 → Spring Boot → STT AI WebSocket 스트리밍 |
| 발신번호 | 시뮬레이터 로그인 또는 사전 설정된 환자 전화번호 |

#### Step 1. 환자 전화 진입

1. 환자가 웹 전화 시뮬레이터에 접속한다.
2. 시스템은 시작 안내 TTS를 송출한다.
   - `안녕하세요, 왔닥입니다. 새로운 예약을 원하시면 1번, 기존 예약 조회·취소를 원하시면 2번을 눌러주세요.`

#### Step 2. 메뉴 선택

1. 환자는 다이얼 패드에서 1번 또는 2번 버튼을 클릭한다.
2. 입력은 시뮬레이터 UI의 버튼 클릭 이벤트로 처리한다.

#### Case 1. 신규 예약

1. 환자가 1번을 입력한다.
2. 시스템은 발신번호(시뮬레이터 설정값)로 환자를 1차 조회한다.
   - 매칭 실패 시: "등록된 전화번호를 입력해주세요" → 다이얼 패드로 번호 입력
   - 그래도 실패 시: "이름과 생년월일을 말씀해주세요" → STT
3. 환자 조회 성공 시 다음 TTS를 송출한다.
   - `OOO 어르신, 어디가 불편하신가요?`
4. 환자는 마이크 버튼을 눌러 증상을 말한다.
5. 시스템은 음성 입력을 Spring Boot를 통해 STT AI WebSocket 세션으로 전달하고, partial/final transcript를 수신한다.
6. 시스템은 확정된 transcript를 기반으로 추천 AI REST API를 호출하여 진료과를 1차 분류한다.
7. 시스템은 추천 결과를 TTS로 안내한다.
   - `내과 김OO 선생님, 3월 15일 오전 10시 진료가 가능합니다. 예약하시겠습니까? 네이면 1번, 다른 시간은 2번을 눌러주세요.`
8. 환자가 1번 → 예약 확정. 2번 → 다음 가용 슬롯 안내 (최대 2회).
9. 시스템은 예약을 생성하고 종료 안내 TTS를 송출한다.
10. 시스템은 환자에게 예약 결과를 **휴대전화 문자(SMS)**로 발송한다.
11. 보호자에게는 로그인 후 확인 가능한 알림 또는 진료 예약 조회 경로를 제공한다.

**신규 예약 성공 조건**
- 환자 조회가 성공해야 한다.
- 증상 입력이 수집되어야 한다.
- 진료과 분류 결과가 생성되어야 한다.
- 의사 매칭 또는 예약 슬롯 확정이 완료되어야 한다.
- 예약 생성 결과가 저장되어야 한다.

#### Case 2. 기존 예약 조회·취소

1. 환자가 2번을 입력한다.
2. 시스템은 발신번호로 환자를 조회한다.
3. 시스템은 해당 환자의 기존 예약 존재 여부를 조회한다.

**Case 2-1. 기존 예약이 있는 경우**
1. 시스템은 다음 TTS를 송출한다.
   - `예약 확인은 1번, 예약 취소는 2번을 눌러주세요.`
2. 1번 → 예약 일시, 담당 의사, 현재 상태를 TTS로 안내 후 종료.
3. 2번 → 취소 가능 여부 확인 후 취소 처리. 취소 결과는 **휴대전화 문자(SMS)**로 환자에게 발송한다.

**Case 2-2. 기존 예약이 없는 경우**
1. `조회된 예약이 없습니다. 새로운 예약을 원하시면 1번을 눌러주세요.`
2. 1번 → 신규 예약 흐름(Case 1)으로 이동.
3. 무입력 → 통화 종료.

---

### 6.3 차량 출동 및 진료 전 준비 시나리오

#### Step 3. 차량 출동

1. 예약이 확정되면 관리자가 차량/미션을 배정한다.
2. 시스템은 MISSION을 생성하고 상태를 `DISPATCHED`로 전환한다.
3. 차량(ROS2)은 미션을 수신하고 출동한다.
4. ROS2 → Spring Boot 이벤트 브릿지를 통해 차량 위치/상태를 업데이트한다.

#### Step 4. 중간 장애 복구

1. 이동 중 장애 발생 시 MISSION.phase를 `INCIDENT`로 전환한다.
2. 관제(관리자)는 장애를 확인하고 복구 조치를 수행한다.
3. 복구 완료 후 `EN_ROUTE`로 복귀한다.

#### Step 5. 차량 도착 및 환자 탑승

1. 차량이 목적지 도착 시 MISSION.phase를 `ARRIVED`로 전환한다.
2. 환자가 탑승한다.
3. 관리자 또는 시스템이 탑승 완료를 기록한다.

#### Step 6. 차량 태블릿 진료 시작

1. 환자 탑승 후 차량 태블릿에서 "진료 시작" 버튼을 누른다.
2. 시스템은 MISSION.phase를 `VERIFYING`으로 전환하고 본인확인 플로우를 시작한다.
3. 이 버튼은 환자 측 진료 세션 생성 버튼이 아니라, **본인확인 및 진료 입장 준비를 시작하는 UX 액션**이다.
4. 본인확인 완료 전에는 환자 세션 참가를 허용하지 않는다.

#### Step 7. 본인확인

1. 차량 내 카메라(또는 태블릿)로 환자의 실시간 얼굴 사진을 촬영한다.
2. 촬영된 사진(probe)을 Spring Boot API로 업로드한다.
3. Spring Boot는 DEV/PROD 공통으로 IDV AI 서버에 multipart 본인확인 요청을 전송한다.
   - 요청 필드 예시: `referenceImage`, `probeImage`
4. IDV AI 서버는 얼굴 비교 + 품질 검증(blur/dark/single face) 결과를 반환한다.
5. 결과에 따라:
    - **VERIFIED**: 진료 준비 단계 진행
    - **FAILED (1차)**: 재촬영 유도 (최대 2회 재시도)
    - **FAILED (2차 이상)**: `MANUAL_REVIEW` 상태로 전환, 관리자 개입
6. 본인확인 결과를 저장한다.
7. `VERIFIED`가 되면 환자 측 화면에 확인 상태를 표시하고, 환자 또는 운영자가 "확인" 후 다음 단계로 진행한다.

**본인확인 전제조건**
- 환자의 사전 등록 얼굴 사진(`PATIENT_FACE_REFERENCE`)이 존재해야 한다.
- 사진 미등록 시: 관리자가 환자 정보를 직접 등록하고 얼굴 사진을 등록해야 한다. 미등록 상태에서는 본인확인을 진행할 수 없다.
> **P1 확장 예정**: 첫 방문 현장 얼굴 촬영 후 관리자 승인으로 기준 사진을 등록하는 흐름 지원

#### Step 8. 확인, 바이탈 입력, 진료 세션 참가

1. 본인확인 성공 후 환자 또는 운영자가 "확인"을 누르면 시스템은 진료 세션 참가 준비 단계로 이동한다.
2. MVP에서 바이탈은 **더미 데이터로 전송**한다. 실기기 연동은 하지 않는다.
3. 입력 항목: 심박수, 산소포화도, 수축기/이완기 혈압, 체온 (최소 2종)
4. 입력 주체는 **차량 태블릿(운영 단말, 관리자 인증)** 또는 관리자 화면이다.
5. 바이탈 기록은 `CARE_CASE` 기준으로 저장하며, 1회 업로드는 여러 측정값(`measurements`)을 포함할 수 있다.
6. 저장 항목: 측정 타입, 값, 단위, 입력 시각(`measuredAt`), 입력 출처(`MANUAL`), 유효성 상태
7. 입력된 최신 바이탈은 의사 UI에 표시되어야 한다.
8. 확인 이후 시스템은 해당 케이스에 활성 진료 세션(`READY` 또는 `IN_PROGRESS`)이 존재하는지 확인한다.
9. 활성 진료 세션이 있으면 차량 태블릿은 환자 참가 토큰을 발급받아 환자를 기존 세션에 입장시킨다.
10. 활성 진료 세션이 없으면 차량 태블릿은 `의사 입장 대기` 상태를 표시하고, 세션이 준비되면 환자를 참가시킨다.
11. 환자 측 UI는 "세션 생성"이 아니라 "세션 참가 준비/대기/참가" 상태를 표현해야 한다.

**진료 시작 / 본인확인 / 세션 참가 성공 조건**
- 차량 태블릿에서 "진료 시작" 버튼으로 본인확인 플로우를 시작할 수 있어야 한다.
- 본인확인 성공 후 확인 단계를 거쳐야 세션 참가 준비를 시작할 수 있어야 한다.
- 바이탈 더미 데이터가 케이스 기준으로 저장되어야 한다.
- 차량 태블릿은 본인확인 상태와 세션 존재 여부를 검사할 수 있어야 한다.
- 환자 측 UI는 "세션 생성"이 아니라 "세션 참가 준비/대기/참가" 상태를 표현해야 한다.

### 6.4 의사 진료 참여 시나리오

1. 의사가 웹페이지에 로그인한다.
2. 의사는 자신에게 배정된 예약과 케이스를 확인한다.
3. 의사는 환자 측에서 "진료 시작" 요청이 들어오고 `VERIFICATION.status = VERIFIED`가 된 케이스를 확인한다.
4. 의사가 "진료 시작"을 클릭하면 시스템은 `POST /cases/{caseId}/sessions`에 해당하는 흐름으로 **의사 전용 진료 세션을 생성**하고, 의사 본인의 WebRTC 토큰만 발급한다.
5. 진료 세션 생성 권한은 **배정된 의사만** 가진다. 환자/차량 태블릿은 진료 세션을 생성하지 않는다.
6. 세션 생성 후 상태는 `READY`가 되며, 확인 단계를 마친 차량 태블릿(운영 단말, 관리자 인증)은 `POST /sessions/{sessionId}/participants/patient/token`에 해당하는 흐름으로 환자 토큰을 발급받는다.
7. 환자 토큰 발급 시 서버는 다음을 검증해야 한다.
    - 요청한 환자가 케이스의 환자와 일치하는지
    - 본인확인 상태가 `VERIFIED`인지
    - 세션 상태가 `READY` 또는 `IN_PROGRESS`인지
8. 의사와 환자가 모두 입장하면 세션 상태를 `IN_PROGRESS`로 전환한다.
9. 의사는 환자 기본 정보, 증상 분류 결과, 최신 바이탈 측정값을 확인하며 진료한다.
10. 진료 종료 후 의사는 진료 요약, 처방 여부, 재진 필요 여부를 기록한다. (기록만 P0, 실제 후속 예약 생성은 P1)
11. 진료 종료 시 세션 상태를 `COMPLETED`로 전환하고 종료 시각, 소요 시간, 요약 정보를 저장한다.

**의사 진료 요구사항**
- 의사는 자신에게 배정된 건만 조회 가능해야 한다.
- 의사 UI 최소 표시 항목: 환자 기본 정보, 예약 정보, 증상 분류 결과, 최신 바이탈 측정값, 세션 연결 상태
- 본인확인 미완료(VERIFICATION.status ≠ VERIFIED) 시 진료 시작 불가
- 케이스당 활성 진료 세션은 최대 1개만 허용해야 한다.
- 환자 측 입장은 본인확인 성공 및 확인 완료 후, 의사가 생성한 세션이 있을 때만 허용해야 한다.

### 6.9 MVP 완료 기준

1. 환자가 웹 전화 시뮬레이터로 신규 예약을 생성할 수 있다.

4. 중간 장애 1회에 대해 관제 복구가 가능하다.

6. 바이탈 더미 데이터 2종 이상이 입력되고 의사 UI에 표시된다.

8. 의사가 진료 요약, 처방 여부, 재진 필요 여부를 기록할 수 있다.

11. 예외 상황에서도 데모가 중단되지 않는다.

## 7. 기능 요구사항

### 7.1 웹 전화 시뮬레이터

- React 기반 전화 다이얼 패드 UI를 제공해야 한다.
- 다이얼 버튼 클릭은 별도 메뉴 입력 저장 API 없이 다음 도메인 API를 직접 호출한다.
- TTS 안내 문구를 음성으로 재생해야 한다.
- 마이크 음성 입력을 받아 Spring Boot를 통해 STT AI WebSocket 스트리밍 세션으로 전달해야 한다.
- 시뮬레이터는 발신번호(환자 전화번호)를 사전 설정/입력할 수 있어야 한다.
- 각 안내 문구와 사용자 입력 이력을 저장해야 한다.

### 7.2 환자 식별

- 1차: 발신번호(시뮬레이터 설정값)로 자동 조회한다.
- 2차(실패 시): 전화번호 직접 입력(다이얼 패드)으로 조회한다.
- 3차(실패 시): 이름 + 생년월일 6자리를 STT로 입력받아 조회한다.
- 전화번호 바인딩 테이블(`PATIENT_PHONE_BINDING`)로 관리한다.
- 본인확인 실패 시 재시도 또는 운영자 개입 경로가 있어야 한다.

### 7.3 인테이크 세션

- 인테이크는 예약 이전에 별도 세션으로 관리한다.
- `INTAKE_SESSION → INTAKE_TURN → SYMPTOM_INTAKE → RECOMMENDATION → BOOKING` 구조를 따른다.
- **세션 생성 시 환자가 아직 식별되지 않을 수 있다.** `patient_id`는 nullable이며, 환자 식별 완료 후 바인딩한다.
- 세션 시작/종료 시각, 상태를 저장한다.
- 턴별 프롬프트, STT 결과, 예외 코드를 저장한다.

### 7.4 증상 분류 및 추천

- 증상 원문 텍스트를 저장한다.
- 1차 증상 분류 결과와 진료과/의사 추천 결과를 저장한다.
- 추천 근거를 남긴다.
- 분류 실패 시 일반과(가정의학과) 기본 배정. `RECOMMENDATION.confidence = LOW`.
- 응급 의심 시 일반 예약보다 우선 경고 안내를 제공한다.

### 7.5 예약 관리

- 신규 예약 생성, 기존 예약 조회, 예약 취소를 지원한다.
- 예약은 환자, 지역, 추천 결과, 의사, 슬롯, 채널과 연결된다.
- 예약 시 환자가 추천 결과를 확인하고 수락/거절할 수 있다.

### 7.6 케이스 관리

- 예약 이후 진료 단위인 케이스를 생성한다.
- 예약과 케이스는 1:1 기준으로 관리한다.

### 7.7 미션/운영 관리

- 출동/현장 운영 단위를 미션으로 관리한다.
- 미션은 케이스와 연결된다.
- 미션 단계, 이벤트, 경고, 결과를 기록한다.
- ROS2 → Spring Boot 이벤트 브릿지로 차량 상태를 연동한다.

### 7.8 본인확인

- **사전 등록 얼굴 사진**과 **실시간 카메라 촬영 사진**을 비교한다.
- Spring Boot → IDV AI/OCR 전달은 DEV/PROD 공통으로 REST multipart를 사용해야 한다.
- Spring Boot ↔ STT AI 통신은 실시간 transcript 생성을 위해 WebSocket 스트리밍을 사용해야 한다.
- Spring Boot → 추천 AI 통신은 최종 transcript 기준으로 REST JSON을 사용해야 한다.
- IDV AI 검증 항목: 얼굴 감지, 단일 얼굴 여부, blur/dark 품질, similarity threshold
- 재시도 최대 2회. 3차 실패 시 MANUAL_REVIEW.
- `VERIFICATION.status ≠ VERIFIED`이면 WebRTC 토큰 발급 금지.
- 환자 사전 등록 사진은 관리자가 직접 등록 및 수정한다.
- 첫 방문 현장 촬영 후 관리자 승인으로 기준 사진을 등록하는 흐름은 P1 범위다.

#### 7.8.1 확장형 본인확인 (P1 선택)

- P1에서는 환자가 **얼굴 사진**과 **신분증 사진**을 각각 UI 가이드라인에 맞춰 촬영하는 확장형 본인확인을 지원할 수 있다.
- 차량 태블릿은 얼굴 이미지와 신분증 이미지를 Spring Boot로 업로드하고, Spring Boot는 두 이미지를 GPU 서버(IDV/OCR 서버)로 전달한다.
- GPU 서버는 신분증 이미지에서 OCR로 `이름`, `생년월일 또는 주민등록번호 마스킹값`, `주소`를 추출한다.
- GPU 서버는 다음 비교 점수를 JSON으로 반환할 수 있다.
  - 실시간 얼굴 vs 사전 등록 얼굴
  - 실시간 얼굴 vs 신분증 얼굴
  - 신분증 얼굴 vs 사전 등록 얼굴
- Spring Boot는 OCR 결과와 환자 기본정보를 대조하여 최종 `VERIFIED`, `FAILED`, `MANUAL_REVIEW`를 판정한다.
- 주민등록번호 전체 원문은 DB에 저장하지 않는 것을 원칙으로 하며, 비교에는 `마스킹값` 또는 `해시`만 사용한다.
- OCR 신뢰도가 낮거나 주소/이름 불일치가 있는 경우 `reasonCodes`에 포함하고 `MANUAL_REVIEW`로 전환할 수 있어야 한다.
- 이 확장형 본인확인은 현재 MVP 기본 경로가 아니라 **선택형 확장안**이다.

### 7.9 동의 기록 (P1)

- MVP에서는 동의 UI 및 동의 기록 기능을 제외한다.
- P1에서 별도 UI를 통해 비대면 진료 동의, 개인정보 처리 동의를 수집하고 저장한다.
- P1에서 `PATIENT_CONSENT` 엔티티로 관리한다.

### 7.10 바이탈 기록 (더미 데이터)

- MVP에서는 실기기 연동 없이 **더미 데이터를 수동 입력**한다.
- 바이탈 기록은 `CARE_CASE` 단위로 저장한다.
- 1회 기록은 여러 측정값(`measurements`)을 포함할 수 있다.
- SpO2, 혈압, 체온, 심박수 중 최소 2종을 저장한다.
- 입력 시각, 입력 출처(`MANUAL`), 측정 타입, 값, 단위, 유효성 상태를 저장한다.
- 차량 태블릿(운영 단말, 관리자 인증) 또는 관리자 화면에서 수동 입력 가능해야 한다.
- 최신 바이탈 기록은 의사 UI 조회와 진료 중 참고 정보로 사용해야 한다.

### 7.11 화상진료 세션

- 케이스당 1:1 진료 세션(의사-환자)을 생성한다.
- LiveKit 기반 WebRTC를 사용하고, **TURN 릴레이를 필수로 구성**한다.
- Spring Boot가 룸 생성 정책과 참여자 토큰을 관리한다.
- 환자 측 차량 태블릿의 "진료 시작" 버튼은 본인확인 및 세션 참가 준비 흐름의 시작점이다.
- 진료 세션 생성 주체는 **배정된 의사**다.
- 환자/차량 태블릿은 진료 세션을 생성하지 않고, 의사가 생성한 세션에만 참가한다.
- 차량 태블릿(운영 단말, 관리자 인증)은 환자 참가 토큰 발급 주체다.
- 세션 상태, 입장/퇴장 시각, 재연결 횟수를 저장한다.
- 의사 세션 생성 시 의사 토큰만 발급하고, 환자 토큰은 별도 엔드포인트에서 발급한다.
- 본인확인 완료 후에만 환자 토큰을 발급한다.
- 본인확인 완료 후 환자 또는 운영자의 확인 단계를 거쳐야 환자 참가를 시도할 수 있다.
- 활성 세션이 없는 경우 차량 태블릿은 "의사 입장 대기" 상태를 표시해야 한다.
- 네트워크 품질 저하 시: 비디오 자동 비활성화 → 오디오만 유지 (fallback).
- 참가자 연결 끊김 30초 초과 시 세션 ABANDONED 판정.
- 토큰 만료 시 프론트에서 재발급 요청 가능 (세션 IN_PROGRESS인 경우만).

### 7.12 보호자 (MVP: 읽기 전용)

- 보호자는 로그인 후 연결된 환자의 진료 요약만 조회한다.
- 환자-보호자 연결은 관리자가 사전 등록한다.
- 보호자 접근 이력은 감사 로그에 남긴다.

### 7.13 웹 로그인

- 관리자, 의사, 보호자는 아이디/비밀번호로 로그인한다.
- 로그인 성공 시 Access Token(응답 Body) + Refresh Token(HttpOnly 쿠키)을 발급한다.
- Access Token은 JS 메모리 변수에 저장하고, API 호출 시 `Authorization: Bearer` 헤더로 전송한다.
- Refresh Token은 HttpOnly 쿠키로 저장하고 `/api/v1/auth` 하위 경로(login, refresh, logout)에만 전송된다.
- 로그아웃 및 세션 만료 처리가 가능하다.

### 7.14 인증/세션 보안

- Refresh Token: HttpOnly, Secure(운영), SameSite=Strict, Path=/api/v1/auth
- Token Rotation: 갱신 시 새 RT 발급 + 이전 RT 무효화
- CSRF: Authorization 헤더 기반이므로 **CSRF 토큰 불필요**
- 계정 비활성화 시 기존 세션 무효화 (`AUTH_SESSION`)

### 7.15 권한 관리

- 관리자/의사/보호자는 역할별 권한(RBAC)으로 분리한다.
- 의사: 배정된 건만 접근
- 보호자: 연결된 환자의 완료 진료 요약만 조회
- 관리자: 전체 운영 데이터 접근

### 7.16 알림

- **환자 알림 채널: 휴대전화 문자(SMS)** — SOLAPI 게이트웨이를 통해 예약 생성/취소 결과를 환자에게 SMS로 발송한다.
- **의사/관리자/보호자 알림 채널: 웹 내 알림** — SSE(폴리필) 또는 Polling 방식으로 실시간 알림을 제공한다.
- 예약 생성/취소, 진료 시작 전 알림
- 개발 환경에서는 SMS를 실제 발송하지 않고 로그 기록으로 대체한다 (Mock).

### 7.17 감사 로그

- 로그인, 로그아웃, 예약 생성/취소, 본인확인 시도/결과, 세션 입장, 진료 종료 등을 기록한다.
- 최소 필드: `log_id`, `timestamp`, `actor_id`, `actor_role`, `action`, `target_type`, `target_id`, `correlation_id`, `detail_json`

## 8. 주요 상태 정의

### 8.1 BOOKING.status
`CONFIRMED` → `CANCELLED` | `COMPLETED` | `NO_SHOW`

### 8.2 CARE_CASE.status
`CREATED` → `PREPARING` → `IN_PROGRESS` → `COMPLETED` | `FAILED` | `CANCELLED`

### 8.3 MISSION.phase
`CREATED` → `DISPATCHED` → `EN_ROUTE` → `ARRIVED` → `VERIFYING` → `CONSULTING` → `RETURNING` → `COMPLETED` | `FAILED`
※ `INCIDENT`는 어느 단계에서든 진입 가능한 임시 상태이며, 복구 후 이전 단계로 복귀한다.

### 8.4 CONSULTATION_SESSION.status
`CREATED` → `READY` → `IN_PROGRESS` → `COMPLETED` | `FAILED` | `ABANDONED`

세션 상태(status)와 참가자 연결 상태(connection_state)는 분리한다.
- `status`: 세션 자체의 라이프사이클 (위 enum)
- `doctor_connection_state` / `patient_connection_state`: `CONNECTED` | `RECONNECTING` | `DISCONNECTED`
- 재연결 중에도 세션 status는 `IN_PROGRESS`를 유지한다.

### 8.5 VERIFICATION.status
`PENDING` → `IN_PROGRESS` → `VERIFIED` | `FAILED` | `MANUAL_REVIEW` | `TIMEOUT`

### 8.6 INTAKE_SESSION.status
`STARTED` → `IN_PROGRESS` → `COMPLETED` | `ABANDONED` | `FAILED`

## 9. 비기능 요구사항

### 9.1 안정성
- 데모 중 핵심 시나리오가 끊기지 않아야 한다.
- 네트워크 장애, 세션 재연결 상황에서도 전체 플로우가 중단되지 않아야 한다.

### 9.2 성능 (데모 기준 최소 수치)
| 항목 | 목표 |
|------|------|
| 전화 시뮬레이터 단계 전환 | < 2초 |
| 예약 API 응답 | < 500ms (p95) |
| WebRTC 연결 | < 5초 |
| STT 응답 | < 10초 |
| IDV 응답 | < 10초 |
| 동시 접속 | 최소 3세션 |

### 9.3 보안
- 개인정보와 진료 정보는 저장 및 전송 시 보호해야 한다.
- 비밀번호는 단방향 해시로 저장한다.
- 인증 토큰은 안전한 쿠키 정책을 사용한다.

### 9.4 추적 가능성
- 예약/케이스/미션/세션은 서로 연결되어야 한다.
- `correlation_id`를 통해 전 구간 흐름 추적이 가능해야 한다.
- 감사 로그로 행위 추적이 가능해야 한다.

### 9.5 운영성
- 운영자는 실패 예약, 미배정 상태, 세션 오류를 확인할 수 있어야 한다.
- 수동 조치가 가능한 관리 화면이 필요한다.

## 10. 권장 데이터 모델 원칙

- 환자 원본 생년월일과 조회용 6자리 키를 분리한다.
- 전화번호는 `PATIENT_PHONE_BINDING` 테이블로 분리한다.
- 예약 전 인테이크를 별도 엔티티로 분리한다.
- 예약, 케이스, 미션, 진료 세션을 각각 분리한다.
- 이미지 파일은 DB에 상대경로로 저장한다 (절대경로 금지).
- 파일명은 UUID 기반으로 생성한다.
- **이중 ID 전략**: 내부 PK는 `bigint` 자동 증가, 외부 API에는 `public_id`(접두사 + nanoid, 예: `pat_V1StGXR8`)를 노출한다.

## 15. 완료 기준

다음 조건을 모두 만족하면 MVP 1차 완료로 판단한다.

1. 환자가 웹 전화 시뮬레이터로 신규 예약을 생성할 수 있다.
2. 환자가 기존 예약을 조회 또는 취소할 수 있다.
3. 증상 입력(STT)과 추천 결과가 저장된다.
4. 예약 후 케이스가 생성된다.
5. 운영자는 미션 및 상태를 확인할 수 있다.
6. 사전 등록 사진 기반 본인확인이 동작한다.
7. 의사는 웹 로그인 후 1:1 진료 세션에 참여할 수 있다.
8. 의사는 진료 요약, 처방 여부, 재진 필요 여부를 기록할 수 있다.
9. 보호자는 웹 로그인 후 진료 요약을 조회할 수 있다.
10. 바이탈 더미 데이터가 입력되고 의사 UI에 표시된다.
11. 감사 로그가 기록된다.
12. 예외 상황에서도 데모가 중단되지 않는다.

### 16.1 구현 순서 가이드

1. `CONSULT-01`에서 리소스 모델을 먼저 고정한다.
2. `CONSULT-02`와 `CONSULT-03`으로 진료 준비 상태를 조회/저장 가능하게 만든다.
3. `CONSULT-04`~`CONSULT-07`로 세션 생성, 참가, 상태 관리, 종료 기록을 순차 구현한다.
4. `CONSULT-08`, `CONSULT-09`에서 차량 태블릿/의사 UI를 실제 API에 연결한다.
5. `CONSULT-10`에서 RBAC, 감사 로그, 통합 시나리오를 마감한다.
