# 도서·산간 방문형 비대면 진료 서비스 — MVP 요구사항 계획서 v2

## 1. 문서 목적

본 문서는 도서·산간 의료취약지 비대면 진료 서비스의 MVP 범위, 시나리오, 기능/비기능 요구사항, 일정 및 리스크를 정의한다.

- MVP 범위를 명확히 고정한다.
- 데모 기준에서 반드시 동작해야 하는 핵심 흐름을 정의한다.
- 개발, 기획, 운영이 같은 기준으로 의사결정할 수 있게 한다.
- ERD, API, 화면 설계, Jira 분해의 상위 기준 문서로 사용한다.

### v1 → v2 주요 변경사항

| 항목 | v1 | v2 |
|------|----|----|
| 전화 채널 | 구현 방식 미정 | **웹 전화 시뮬레이터** (React 기반) |
| 현장 신원 확인 | "신분증 + 카메라" (불명확) | **차량 촬영 얼굴 사진 + 기존 기준 이미지 + 신분증 이미지 GPU 비교** |
| 보호자 MVP 범위 | 포함/제외 모순 | **읽기 전용만 MVP** (3자 WebRTC는 P1) |
| 예약 변경 | 포함/제외 모순 | **MVP 제외** (P1). 조회·취소만 P0 |
| 추가 측정 데이터 | 실측 전제 | **MVP 제외** |
| 처방/후속예약 | P0/P1 불명확 | **기록만 P0**, 실제 생성/연계는 P1 |
| 상태 enum | 미정의 | 주요 엔티티별 상태 정의 포함 |
| 프론트엔드 | 미명시 | React 명시 |

## 2. 프로젝트 개요

의료취약지 환자가 **앱 설치 없이 웹 전화 시뮬레이터**로 진료를 예약하고, 이후 의사와 원격 화상진료를 진행할 수 있도록 지원하는 서비스다.

MVP 핵심 흐름:

**웹 전화 시뮬레이터 진입 → 환자 식별 → DTMF 진료과 선택 → 진료과/의사 매칭 → 예약 생성 → 예약 결과 SMS 발송 → 케이스 생성 → 미션/출동 관리 → 차량 태블릿 진료 시작 → 미션 단계 전환 및 진료 준비 → 진료 세션 참가(WebRTC) → 진료 요약/처방 여부 기록 → 운영 로그**

예약, 진료 준비, 실제 진료, 운영 추적은 서로 다른 라이프사이클을 가지므로, **BOOKING**, **CARE_CASE**, **MISSION**, **CONSULTATION_SESSION**을 분리한다.

## 3. MVP 목표

### 3.1 비즈니스 목표

- 의료취약지 환자가 웹 전화 시뮬레이터로 예약을 완료할 수 있어야 한다.
- 환자와 의사가 원격 진료에 실제로 참여할 수 있어야 한다.
- 운영자가 예약부터 진료 종료까지 상태를 추적할 수 있어야 한다.

### 3.2 제품 목표

- 웹 전화 시뮬레이터 기반 신규 예약, 예약 조회, 예약 취소
- DTMF 기반 진료과 선택 및 의사 매칭
- 진료과 선택 결과 저장 및 의사 매칭
- 예약 결과 SMS 발송
- 케이스 및 운영 단위 생성
- 1:1 화상진료 (의사-환자)
- 보호자/의사 회원가입 신청 및 관리자 승인
- 보호자 로그인 및 진료 요약 조회 (읽기 전용)
- 로그인, 접근 권한, 세션, 운영 로그 관리

### 3.3 데모 성공 기준

1. 신규 예약 시나리오가 처음부터 끝까지 끊기지 않고 동작한다.
2. 기존 예약 조회/취소가 동작한다.
3. 차량 태블릿에서 미션 단계 전환과 진료 준비가 동작한다.
4. 1:1 WebRTC 화상진료가 동작한다.
5. 예외 상황에서도 시스템이 죽지 않고 복구 멘트 또는 대체 경로를 제공한다.
6. 운영자가 예약·케이스·세션 상태를 확인할 수 있다.
7. 예약 생성/취소 후 환자 휴대전화로 결과 SMS가 발송된다.
8. 보호자와 의사가 관리자 승인 뒤 로그인할 수 있으며, 보호자는 환자 휴대전화 번호로 가입 신청 후 승인되면 진료 요약을 조회할 수 있다.

## 4. 프로젝트 범위

### 4.1 MVP 포함 범위

- 웹 전화 시뮬레이터 기반 진입 (React)
- 생년월일 6자리 + 발신번호 기반 환자 식별
- 인테이크 세션 관리
- DTMF 기반 진료과 선택
- 진료과 선택 결과 저장 및 의사 매칭
- 예약 생성, 조회, 취소
- 예약 결과 SMS 발송
- 케이스 생성
- 미션/운영 상태 관리
- 의사 / 관리자 / 보호자 웹 로그인
- Access Token(localStorage via Zustand) + Refresh Token(HttpOnly 쿠키) 인증
- 보호자/의사 회원가입 신청 및 관리자 승인
- GPU 서버 기반 본인 확인 (차량 촬영 얼굴 사진 + 기존 기준 이미지 + 신분증 이미지 비교)
- 1:1 화상진료 세션 생성 및 참여 (LiveKit WebRTC + TURN)
- 진료 요약, 처방 여부, 재진 필요 여부 기록
- 보호자 로그인 및 진료 요약 조회 (읽기 전용)
- 운영 로그

### 4.2 MVP 제외 범위

- 실제 전화망(PSTN) 연동
- **예약 변경** (슬롯 반환/재점유, 동시성 처리 비용이 높으므로 P1)
- 본인확인 결과 별도 영속 테이블/리소스 관리
- 동의 UI 및 동의 기록
- 보호자 실시간 3자 WebRTC 진료 참여
- 보호자 접근 권한 세밀 관리
- 별도 측정 데이터 입력/저장 도메인
- 후속 예약 실제 생성 (MVP는 재진 필요 여부 기록만)
- 처방 시스템 연계/고도화 처방 관리 (MVP는 처방 여부 기록만)
- 웹 내 알림 저장/조회
- 고도화된 AI 진단
- 소셜 로그인
- 정식 EMR 완전 통합
- 자동 배차 최적화 고도화
- 고급 분석 대시보드

## 5. 사용자 정의

### 5.1 환자
- 웹 전화 시뮬레이터로 서비스에 진입한다.
- 신규 예약, 기존 예약 조회, 예약 취소를 수행할 수 있다.
- 차량 배정 이후 운영자 안내에 따라 진료 세션에 참가한다.

### 5.2 보호자 (MVP: 읽기 전용)
- 환자 휴대전화 번호와 관계 정보를 입력해 회원가입을 신청한다.
- 관리자 승인 후 웹페이지에 로그인한다.
- 본인에게 연결된 환자의 진료 요약 내용을 확인할 수 있다.
- **MVP에서는 실시간 WebRTC 진료 참여 불가** (P1 확장).

### 5.3 의사
- 웹페이지에 로그인한다.
- 자신에게 배정된 예약, 케이스, 세션에 접근한다.
- 진료 시작, 종료, 요약 입력, 처방 여부/재진 필요 여부 기록이 가능하다.
- **후속 예약 실제 생성은 P1.**

### 5.4 관리자
- 웹페이지에 로그인한다.
- 환자, 예약, 케이스, 미션, 세션, 예외 상태를 관리한다.
- 보호자 가입 요청을 승인/반려한다.

## 6. MVP 핵심 시나리오

### 6.1 시나리오 개요

환자가 **웹 전화 시뮬레이터**로 신규 예약을 생성하거나 기존 예약을 조회·취소하고, 예약된 차량이 출동하여 환자를 탑승시킨 뒤, 차량 태블릿에서 **진료 시작**을 누르고 미션 단계를 전환하며 진료 준비를 진행한 후 1:1 WebRTC 비대면 진료에 참가한다.

---

### 6.2 환자 전화 진입 및 예약 시나리오

#### 전화 시뮬레이터 기술 구현

| 항목 | 구현 방식 |
|------|-----------|
| 전화 진입 | React 웹 전화 시뮬레이터 UI |
| 메뉴 버튼 입력 | 화면 다이얼 패드 버튼 클릭 후 다음 API 직접 호출 |
| TTS 송출 | Web Speech API 또는 서버 TTS 음성 파일 재생 |
| 신규 예약 입력 | 다이얼 패드(DTMF) 기반 진료과 선택, `0번` 다시 듣기 |
| 발신번호 | 시뮬레이터 로그인 또는 사전 설정된 환자 전화번호 |

#### Step 1. 환자 전화 진입

1. 환자가 웹 전화 시뮬레이터에 접속한다.
2. 시스템은 시작 안내 TTS를 송출한다.
   - `안녕하세요, 왔닥입니다. 새로운 예약을 원하시면 1번, 기존 예약 조회·취소를 원하시면 2번을 눌러주세요.`

#### Step 2. 메뉴 선택

1. 환자는 다이얼 패드에서 1번 또는 2번 버튼을 클릭한다.
2. 입력은 시뮬레이터 UI의 버튼 클릭 이벤트로 처리한다.

#### Case 1. 신규 예약

1. 환자가 1번을 입력한다.
2. 시스템은 발신번호(시뮬레이터 설정값)로 환자를 1차 조회한다.
   - 매칭 실패 시: "등록된 전화번호를 입력해주세요" → 다이얼 패드로 번호 입력
   - 운영 정책에 따라 추가 식별 수단을 둘 수 있으나, MVP 기본 흐름은 DTMF 중심으로 유지한다.
3. 환자 조회 성공 시 시스템은 신규 예약용 진료과 메뉴를 TTS로 송출한다.
   - `원하시는 진료과를 선택해주세요. 내과는 1번, 피부과는 2번, 정형외과는 3번, 신경과는 4번, 안과는 5번, 다시 듣기는 0번입니다.`
4. 환자는 다이얼 패드로 진료과를 선택한다.
5. 시스템은 선택한 진료과에 대한 환자의 과거 진료 이력을 확인한다.
6. 같은 진료과 진료 이력이 있으면, 해당 진료과에서 마지막으로 진료한 의사를 우선 매칭한다.
7. 우선 매칭 의사의 가용 슬롯이 없으면 같은 진료과의 다른 의사 슬롯으로 fallback 한다.
8. 시스템은 가장 적절한 가용 슬롯을 TTS로 안내한다.
   - `내과 김OO 선생님, 3월 15일 오전 10시 진료가 가능합니다. 예약하시겠습니까? 예약은 1번, 다른 시간은 2번, 다시 듣기는 0번입니다.`
9. 환자가 1번 → 예약 확정. 2번 → 다음 가용 슬롯 안내 (최대 2회). 0번 → 현재 슬롯 안내 반복.
10. 시스템은 예약을 생성하고 종료 안내 TTS를 송출한다.
11. 시스템은 예약 결과를 TTS 및 화면 상태로 안내한다.
12. 보호자는 로그인 후 연결된 환자의 예약/진료 결과를 조회한다.

**신규 예약 성공 조건**
- 환자 조회가 성공해야 한다.
- 진료과 선택 입력이 수집되어야 한다.
- 동일 진료과 이력 조회 또는 fallback 의사 매칭이 완료되어야 한다.
- 의사 매칭 및 예약 슬롯 확정이 완료되어야 한다.
- 예약 생성 결과가 저장되어야 한다.

#### Case 2. 기존 예약 조회·취소

1. 환자가 2번을 입력한다.
2. 시스템은 발신번호로 환자를 조회한다.
3. 시스템은 해당 환자의 기존 예약 존재 여부를 조회한다.

**Case 2-1. 기존 예약이 있는 경우**
1. 시스템은 다음 TTS를 송출한다.
   - `예약 확인은 1번, 예약 취소는 2번을 눌러주세요.`
2. 1번 → 예약 일시, 담당 의사, 현재 상태를 TTS로 안내 후 종료.
3. 2번 → 취소 가능 여부 확인 후 취소 처리. 취소 결과는 TTS 및 화면 상태로 안내한다.

**Case 2-2. 기존 예약이 없는 경우**
1. `조회된 예약이 없습니다. 새로운 예약을 원하시면 1번을 눌러주세요.`
2. 1번 → 신규 예약 흐름(Case 1)으로 이동.
3. 무입력 → 통화 종료.

---

### 6.3 차량 출동 및 진료 전 준비 시나리오

#### Step 3. 차량 출동

1. 예약이 확정되면 관리자가 차량/미션을 배정한다.
2. 시스템은 MISSION을 생성하고 상태를 `DISPATCHED`로 전환한다.
3. 차량(ROS2)은 미션을 수신하고 출동한다.
4. ROS2 → Spring Boot 이벤트 브릿지를 통해 차량 위치/상태를 업데이트한다.

#### Step 4. 중간 장애 복구

1. 이동 중 장애 발생 시 MISSION.phase를 `INCIDENT`로 전환한다.
2. 관제(관리자)는 장애를 확인하고 복구 조치를 수행한다.
3. 복구 완료 후 `EN_ROUTE`로 복귀한다.

#### Step 5. 차량 도착 및 환자 탑승

1. 차량이 목적지 도착 시 MISSION.phase를 `ARRIVED`로 전환한다.
2. 환자가 탑승한다.
3. 관리자 또는 시스템이 탑승 완료를 기록한다.

#### Step 6. 차량 태블릿 진료 시작

1. 환자 탑승 후 차량 태블릿에서 "진료 시작" 버튼을 누른다.
2. 시스템은 MISSION.phase를 `VERIFYING`으로 전환하고 진료 준비 플로우를 시작한다.
3. 이 버튼은 환자 측 진료 세션 생성 버튼이 아니라, **미션 단계 전환과 환자 입장 준비를 시작하는 UX 액션**이다.
4. 활성 진료 세션이 없더라도 차량 태블릿은 본인확인과 활력징후 단계까지 진행할 수 있으며, 진료실 입장 직전에는 `의사 입장 대기` 상태를 유지한다.

#### Step 7. 본인 확인

1. 차량 태블릿은 환자 얼굴 사진과 신분증 이미지를 촬영한다.
2. 서버는 `patientId` 기준으로 운영 저장소에 보관된 기존 기준 이미지를 조회한다.
3. 서버는 기준 이미지가 있으면 `referenceImage`, `faceImage`, `idCardImage`를, 없으면 `faceImage`, `idCardImage`만 GPU 서버로 전송하고 일치도/판정 응답을 받는다.
4. GPU 서버 응답에는 최소 `matched`, `faceSimilarityScore`, `idCardFaceSimilarityScore`, `reasonCodes`, `ocr.name`, `ocr.rrn`, `ocr.address`가 포함되어야 한다.
5. 서버는 GPU OCR 결과의 이름, 주소, 주민등록번호 기반 생년월일을 현재 환자 정보와 대조하고, 이름/생년월일 6자리/주소 중 하나 이상 일치하면 통과로 판정한다.
6. 서버는 별도 본인확인 결과 테이블은 두지 않되, 활력징후 단계와 환자 토큰 발급 사이에서 사용할 수 있도록 TTL 기반 캐시에 최근 성공 상태를 저장한다.
7. 본인 확인 성공 시 차량 태블릿은 활력징후 단계로 이동하고, 실패 시 재촬영 또는 운영자 개입 경로를 제공한다.

#### Step 8. 세션 준비 및 진료 세션 참가

1. 운영자는 차량 태블릿에서 본인 확인 성공 여부와 진료 준비 상태를 확인한다.
2. 활력징후 단계는 UX에 포함하되, MVP에서는 측정값 영속 저장 없이 장비 연동 또는 더미 표시 수준까지 허용한다.
3. 시스템은 케이스, 미션 단계, 활성 진료 세션 존재 여부를 함께 조회한다.
4. 활성 진료 세션이 없으면 차량 태블릿은 활력징후 완료 후 `의사 입장 대기` 화면을 유지하고, 세션이 준비되면 다음 단계로 진행한다.
5. 활성 진료 세션이 있으면 차량 태블릿은 `POST /missions/{missionId}/participants/patient/token`으로 환자 참가 토큰을 요청하고, 서버가 `missionId -> case -> consultationSession -> patient`로 대상 세션과 환자를 결정한다.
6. 서버는 최근 본인 확인 성공 상태가 유효할 때만 환자 토큰을 발급한다.
7. 의사와 환자가 모두 입장하면 세션 상태를 `IN_PROGRESS`로 전환하고, 미션 단계도 `CONSULTING`으로 전환한다.
8. 환자 측 UI는 "세션 생성"이 아니라 "세션 참가 준비/대기/참가" 상태를 표현해야 한다.

**진료 시작 / 본인확인 / 세션 참가 성공 조건**
- 차량 태블릿에서 "진료 시작" 버튼으로 진료 준비 플로우를 시작할 수 있어야 한다.
- 차량 태블릿은 GPU 서버 본인 확인 결과를 확인할 수 있어야 한다.
- 차량 태블릿은 본인 확인 성공 후 활력징후 단계로 이동할 수 있어야 한다.
- 서버는 본인 확인 성공 시에만 환자 참가 토큰을 발급해야 한다.
- 환자 측 UI는 "세션 생성"이 아니라 "세션 참가 준비/대기/참가" 상태를 표현해야 한다.

---

### 6.4 의사 진료 참여 시나리오

1. 의사가 웹페이지에 로그인한다.
2. 의사는 자신에게 배정된 예약과 케이스를 확인한다.
3. 의사는 차량 측에서 진료 준비가 시작된 케이스를 확인한다.
4. 의사가 "진료 시작"을 클릭하면 시스템은 `POST /cases/{caseId}/sessions`에 해당하는 흐름으로 **의사 전용 진료 세션을 생성**하고, 의사 본인의 WebRTC 토큰만 발급한다.
5. 진료 세션 생성 권한은 **배정된 의사만** 가진다. 환자/차량 태블릿은 진료 세션을 생성하지 않는다.
6. 세션 생성 후 상태는 `READY`가 되며, 차량 태블릿(운영 단말, 미션 단말 토큰)은 본인 확인과 활력징후 단계를 거친 뒤 `POST /missions/{missionId}/participants/patient/token`으로 환자 토큰 발급을 요청한다.
7. 환자 토큰 발급 시 서버는 다음을 검증해야 한다.
    - 세션이 연결된 케이스의 환자를 서버가 일관되게 조회할 수 있는지
    - 미션 단계가 환자 참가 가능한 준비 상태(`VERIFYING` 또는 `CONSULTING`)인지
    - 최근 본인 확인 성공 상태가 유효한지
    - 세션 상태가 `READY` 또는 `IN_PROGRESS`인지
8. 의사와 환자가 모두 입장하면 세션 상태를 `IN_PROGRESS`로 전환한다.
9. 의사는 환자 기본 정보, 진료과 선택 결과, 세션 연결 상태를 확인하며 진료한다.
10. 진료 종료 후 의사는 진료 요약, 처방 여부, 재진 필요 여부를 기록한다. (기록만 P0, 실제 후속 예약 생성은 P1)
11. 진료 종료 시 세션 상태를 `COMPLETED`로 전환하고 종료 시각, 소요 시간, 요약 정보를 저장한다.

**의사 진료 요구사항**
- 의사는 자신에게 배정된 건만 조회 가능해야 한다.
- 의사 UI 최소 표시 항목: 환자 기본 정보, 예약 정보, 진료과 선택 결과, 세션 연결 상태
- 차량 측에서 진료 준비가 시작되지 않은 케이스는 진료 시작 대상으로 표시하지 않아야 한다.
- 케이스당 활성 진료 세션은 최대 1개만 허용해야 한다.
- 환자 측 입장은 GPU 본인 확인 성공 및 의사가 생성한 세션이 있을 때만 허용해야 한다.

### 6.5 보호자 시나리오 (MVP: 읽기 전용)

1. 보호자가 회원가입 화면에서 `patientPhone`과 관계를 입력해 가입을 신청한다.
2. 시스템은 `PATIENT.phone`으로 환자를 식별하고 보호자 가입 요청을 `PENDING` 상태로 생성한다.
3. 관리자가 요청을 승인하면 보호자 계정이 활성화된다.
4. 보호자가 웹페이지에 로그인한다.
5. 본인에게 연결된 환자 목록을 확인한다.
6. 완료된 진료의 요약 내용을 조회한다.

> **P1 확장 예정**: 보호자 실시간 3자 WebRTC 참여 및 세밀한 접근 권한 관리

### 6.9 MVP 완료 기준

1. 환자가 웹 전화 시뮬레이터에서 DTMF 기반 진료과 선택으로 신규 예약을 생성할 수 있다.
2. 환자가 기존 예약을 조회 또는 취소할 수 있다.
3. 차량 출동 상태를 기록할 수 있다.
4. 중간 장애 1회에 대해 관제 복구가 가능하다.
5. 차량 태블릿에서 진료 준비를 시작하고 대기/참가 상태를 전환할 수 있다.
6. 1:1 WebRTC 화상진료가 동작한다.
7. 의사가 진료 요약, 처방 여부, 재진 필요 여부를 기록할 수 있다.
8. 보호자가 로그인하여 진료 요약을 조회할 수 있다.
9. 관리자가 예약·케이스·미션·세션 상태를 조회하고 수동 조정할 수 있다.
11. 예외 상황에서도 데모가 중단되지 않는다.

## 7. 기능 요구사항

### 7.1 웹 전화 시뮬레이터

- React 기반 전화 다이얼 패드 UI를 제공해야 한다.
- 다이얼 버튼 클릭은 별도 메뉴 입력 저장 API 없이 다음 도메인 API를 직접 호출한다.
- TTS 안내 문구를 음성으로 재생해야 한다.
- 신규 예약의 핵심 입력은 다이얼 패드(DTMF) 기반 메뉴/진료과 선택으로 처리해야 한다.
- 시뮬레이터는 발신번호(환자 전화번호)를 사전 설정/입력할 수 있어야 한다.
- 각 안내 문구와 사용자 입력 이력을 저장해야 한다.

### 7.2 환자 식별

- 1차: 발신번호(시뮬레이터 설정값)로 자동 조회한다.
- 2차(실패 시): 전화번호 직접 입력(다이얼 패드)으로 조회한다.
- 3차(실패 시): 운영 정책에 따라 재통화 안내 또는 운영자 개입 경로를 제공한다.
- 환자 전화번호는 `PATIENT.phone` 전역 unique 컬럼으로 관리한다.
- 환자 식별 실패 시 재시도 또는 운영자 개입 경로가 있어야 한다.

### 7.3 인테이크 세션

- 인테이크는 예약 이전에 별도 세션으로 관리한다.
- `INTAKE_SESSION(selected_department, selected_department_name, selection_reason, selection_confidence_level, offered_slot_ids_json) → BOOKING` 구조를 따른다.
- **세션 생성 시 환자가 아직 식별되지 않을 수 있다.** `patient_id`는 nullable이며, 환자 식별 완료 후 바인딩한다.
- 세션 시작/종료 시각, 상태를 저장한다.
- 메뉴 선택, 식별, 의사 매칭, 예약 흐름은 운영 로그와 `last_activity_at` 갱신으로 추적한다.

### 7.4 진료과 선택 및 의사 매칭

- 신규 예약은 환자가 다이얼 패드로 진료과를 직접 선택한다.
- 진료과 메뉴는 내과, 피부과, 정형외과, 신경과, 안과를 기본 제공하고 `0번 다시 듣기`를 지원한다.
- 선택된 진료과에 대해 환자의 과거 진료 이력을 확인한다.
- 같은 진료과의 과거 진료 이력이 있으면 마지막으로 진료한 의사를 우선 매칭한다.
- 우선 매칭 의사의 가용 슬롯이 없으면 같은 진료과의 다른 의사로 fallback 한다.
- STT/AI 기반 증상 분류는 MVP 기본 흐름에서 제외하고 향후 확장 항목으로 둔다.

### 7.5 예약 관리

- 신규 예약 생성, 기존 예약 조회, 예약 취소를 지원한다.
- 예약은 환자, 선택 진료과 또는 과거 진료 이력 기반 매칭 결과, 의사, 슬롯, 채널과 연결된다.
- 예약 시 환자가 안내된 슬롯을 수락하거나 다음 슬롯을 선택할 수 있다.

### 7.6 케이스 관리

- 예약 이후 진료 단위인 케이스를 생성한다.
- 예약과 케이스는 1:1 기준으로 관리한다.

### 7.7 미션/운영 관리

- 출동/현장 운영 단위를 미션으로 관리한다.
- 미션은 케이스와 연결된다.
- 미션 단계와 현재 위치(latitude/longitude)를 미션 엔티티에서 직접 관리한다.
- ROS2 → Spring Boot 이벤트 브릿지로 차량 상태를 연동한다.

### 7.8 본인 확인 및 현장 진료 준비

- 차량 태블릿의 "진료 시작" 버튼은 환자 세션 생성이 아니라 **미션 단계 전환과 본인 확인/진료 준비 시작**을 의미한다.
- 본인 확인은 차량에서 촬영한 `faceImage`, `idCardImage`와 운영 저장소의 기존 기준 이미지를 GPU 서버로 보내 일치도를 받는 액션이다.
- GPU 서버 응답에는 최소 `matched`, `faceSimilarityScore`, `idCardFaceSimilarityScore`, `reasonCodes`, `ocr.name`, `ocr.rrn`, `ocr.address`가 포함되어야 한다.
- 서버는 OCR의 `rrn`에서 생년월일 정보를 추출해 환자 `birthDate6`와 대조하고, 이름/주소도 함께 확인한다.
- 서버는 별도 본인확인 엔티티, 결과 테이블은 만들지 않으며, 활력징후 단계와 토큰 발급 사이에서는 TTL 캐시에 최근 성공 상태만 유지한다.
- 운영자는 케이스, 미션, 세션 상태를 함께 조회하며 현장 진행 여부를 판단해야 한다.
- 환자 참가 가능 여부는 케이스-환자 일치, 미션 단계, GPU 본인 확인 결과, 세션 상태를 기준으로 판단한다.

### 7.9 동의 기록 (P1)

- MVP에서는 동의 UI 및 동의 기록 기능을 제외한다.
- P1에서 별도 UI를 통해 비대면 진료 동의, 개인정보 처리 동의를 수집하고 저장한다.
- P1에서 별도 동의 기록 리소스로 관리한다.

### 7.10 추가 측정 데이터 (MVP 제외)

- 별도 측정 데이터 입력/저장 도메인은 이번 MVP 범위에서 제외한다.
- 진료 준비와 세션 참가 판단은 케이스, 미션, 세션 상태 중심으로 처리한다.

### 7.11 화상진료 세션

- 케이스당 1:1 진료 세션(의사-환자)을 생성한다.
- LiveKit 기반 WebRTC를 사용하고, **TURN 릴레이를 필수로 구성**한다.
- Spring Boot가 룸 생성 정책과 참여자 토큰을 관리한다.
- 환자 측 차량 태블릿의 "진료 시작" 버튼은 미션 단계 전환 및 세션 참가 준비 흐름의 시작점이다.
- 진료 세션 생성 주체는 **배정된 의사**다.
- 환자/차량 태블릿은 진료 세션을 생성하지 않고, 의사가 생성한 세션에만 참가한다.
- 차량 태블릿(운영 단말, 관리자 인증)은 환자 참가 토큰 발급 주체다.
- 세션 상태, 입장/퇴장 시각, 재연결 횟수를 저장한다.
- 의사 세션 생성 시 의사 토큰만 발급하고, 환자 토큰은 별도 엔드포인트에서 발급한다.
- 미션 단계가 진료 준비 상태에 도달하고 GPU 본인 확인이 성공한 경우에만 환자 토큰을 발급한다.
- 운영자 확인 단계를 거쳐야 환자 참가를 시도할 수 있다.
- 활성 세션이 없는 경우 차량 태블릿은 "의사 입장 대기" 상태를 표시해야 한다.
- 네트워크 품질 저하 시: 비디오 자동 비활성화 → 오디오만 유지 (fallback).
- 참가자 연결 끊김 30초 초과 시 세션 ABANDONED 판정.
- 토큰 만료 시 프론트에서 재발급 요청 가능 (세션 IN_PROGRESS인 경우만).

### 7.12 보호자 (MVP: 읽기 전용)

- 보호자는 환자 휴대전화 번호와 관계 정보를 입력해 회원가입을 신청한다.
- 시스템은 `PATIENT.phone` 기준으로 대상 환자를 식별하고 보호자 가입 요청을 생성한다.
- 의사와 보호자 계정은 모두 관리자 승인 후에만 활성화된다.
- 승인된 보호자 계정만 연결된 환자의 진료 요약을 조회할 수 있다.
- 보호자 접근 이력은 감사 로그에 남긴다.

### 7.13 웹 로그인

- 관리자, 의사, 보호자는 아이디/비밀번호로 로그인한다.
- 의사와 보호자 계정은 관리자 승인 전까지 로그인할 수 없다.
- 로그인 성공 시 Access Token(응답 Body) + Refresh Token(HttpOnly 쿠키)을 발급한다.
- Access Token은 JS 메모리 변수에 저장하고, API 호출 시 `Authorization: Bearer` 헤더로 전송한다.
- Refresh Token은 HttpOnly 쿠키로 저장하고 `/api/v1/auth` 하위 경로(login, refresh, logout)에만 전송된다.
- 로그아웃 및 세션 만료 처리가 가능하다.

### 7.14 인증/세션 보안

- Refresh Token: HttpOnly, Secure(운영), SameSite=Strict, Path=/api/v1/auth
- Token Rotation: 갱신 시 새 RT 발급 + 이전 RT 무효화
- CSRF: Authorization 헤더 기반이므로 **CSRF 토큰 불필요**
- Refresh Token은 Redis 키(`refresh:{token}`) 기준으로 관리하며, 계정 비활성화 시 관련 RT를 즉시 무효화한다.

### 7.15 권한 관리

- 관리자/의사/보호자는 역할별 권한(RBAC)으로 분리한다.
- 의사: 배정된 건만 접근
- 보호자: 연결된 환자의 완료 진료 요약만 조회
- 관리자: 전체 운영 데이터 접근

### 7.16 환자 안내 및 상태 통지

- 환자 안내는 웹 전화 시뮬레이터의 TTS와 화면 상태 표시를 기본 경로로 사용한다.
- 예약 생성/취소 결과는 환자 기본 휴대전화 번호로 SMS를 발송한다.
- SMS 발송은 예약 처리 성공 후 비동기 후처리로 수행하며, 별도 저장 테이블 없이 운영 로그와 재시도 정책으로 관리한다.
- 운영자와 보호자는 로그인 후 예약/진료 상태를 조회한다.
- 별도 알림 저장/조회 도메인은 이번 MVP 범위에서 제외한다.

### 7.17 감사 로그

- 로그인, 로그아웃, 예약 생성/취소, 인테이크 진행, 미션 단계 전환, 세션 입장, 진료 종료 등을 기록한다.
- 별도 영속 엔티티를 전제하지 않고 `AuditLogService` 등 서비스 레이어에서 운영 로그를 남긴다.
- 최소 컨텍스트: `timestamp`, `actor_id`, `actor_role`, `action`, `target_type`, `target_id`, `correlation_id`, `detail_json`

## 9. 비기능 요구사항

### 9.1 안정성
- 데모 중 핵심 시나리오가 끊기지 않아야 한다.
- 네트워크 장애, 세션 재연결 상황에서도 전체 플로우가 중단되지 않아야 한다.

### 9.2 성능 (데모 기준 최소 수치)
| 항목 | 목표 |
|------|------|
| 전화 시뮬레이터 단계 전환 | < 2초 |
| 예약 API 응답 | < 500ms (p95) |
| WebRTC 연결 | < 5초 |
| 미션/세션 상태 조회 | < 1초 |
| GPU 본인확인 응답 | < 10초 |
| 동시 접속 | 최소 3세션 |

### 9.3 보안
- 개인정보와 진료 정보는 저장 및 전송 시 보호해야 한다.
- 비밀번호는 단방향 해시로 저장한다.
- 인증 토큰은 안전한 쿠키 정책을 사용한다.
- 신분증 OCR로 얻은 주민등록번호 원문은 GPU 응답 처리 중 비교 용도로만 사용하고, 별도 영속 저장이나 외부 API 원문 노출은 금지한다.

### 9.4 추적 가능성
- 예약/케이스/미션/세션은 서로 연결되어야 한다.
- `correlation_id`를 통해 전 구간 흐름 추적이 가능해야 한다.
- 감사 로그로 행위 추적이 가능해야 한다.

### 9.5 운영성
- 운영자는 실패 예약, 미배정 상태, 세션 오류를 확인할 수 있어야 한다.
- 수동 조치가 가능한 관리 화면이 필요한다.

## 15. 완료 기준

다음 조건을 모두 만족하면 MVP 1차 완료로 판단한다.

1. 환자가 웹 전화 시뮬레이터로 신규 예약을 생성할 수 있다.
2. 환자가 기존 예약을 조회 또는 취소할 수 있다.
3. DTMF 진료과 선택 결과와 안내 슬롯 스냅샷이 `INTAKE_SESSION`에 저장된다.
4. 예약 생성/취소 결과 SMS가 환자 기본 휴대전화 번호로 발송된다.
5. 예약 후 케이스가 생성된다.
