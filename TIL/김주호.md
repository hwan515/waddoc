## 행사장 내 혼잡과 대기열 동선 자동 재구성 시스템을 정리한다

## 1) 현장 페인포인트를 “줄”이 아니라 “동선/안전/운영”으로 재정의한다

### 1-1. 안전 페인포인트를 정의한다

* **Spillback(줄 꼬리)로 통로 침범이 발생한다**: 줄이 길어지는 것 자체가 문제가 아니라, **통로(aisle)·비상동선(egress buffer)**을 침범하는 순간 “사고 가능성”이 급증한다.
* **병목구간(jam point)이 고착된다**: 특정 부스/체험존/입구에서 순간 피크가 발생하면 운영팀은 즉각 레이아웃을 바꿔야 하지만 실제로는 **배리어/안내가 늦다**.
* **출입구/소방/비상구 인근 혼잡이 발생한다**: “사람이 몰리는 위치”와 “법/규정상 비워야 하는 위치”가 겹치는 경우가 많다.

### 1-2. 운영 페인포인트를 정의한다

* **사람을 붙여서 줄 세우는 비용이 발생한다**: 안내요원이 줄을 “형성”하고 “유지”하는 데 시간을 소모하여 본업 이탈이 발생한다.
* **매번 레이아웃이 바뀌는 행사 특성이 존재한다**: 부스 위치, 동선, 프로그램 시간표가 바뀌어 “고정 설비”가 아니라 “운영”으로 대응해야 한다.
* **현장 의사결정이 경험에 의존한다**: “어디로 돌릴까”를 숙련자가 즉흥적으로 결정하여 재현성과 사후 개선이 어렵다.

### 1-3. 경험 페인포인트를 정의한다

* **기대보다 긴 대기**와 **줄 위치의 모호함**이 불만을 키운다.
* “줄이 길다”보다 **줄이 불규칙하고 통로를 막으며 끼어들기/충돌이 늘어나는 것**이 UX를 망친다.

## 2) “줄을 어떻게 세울지”의 방식 정의로서 줄 패턴(Queue Pattern) 라이브러리를 구성한다

현장에서 실제로 통하는 줄 패턴은 대략 6~8개면 충분하다고 본다. 중요한 것은 “무한한 모양 생성”이 아니라 **조건별로 가장 안전하고 빠른 패턴을 선택**하는 것이라 정의한다.

### 2-1. 기본 패턴 6종을 정리한다

1. **Straight Queue(직선형)을 사용한다**

* 장점: 가장 직관적이며 안내가 쉽고 진입/이탈이 명확하다.
* 단점: 길어지면 spillback이 즉시 통로로 번진다.
* 추천 조건: 피크가 낮고 충분한 대기 공간 길이가 확보될 때 사용한다.

2. **Serpentine(S자/스위치백)을 사용한다**

* 장점: 동일 면적에서 수용 인원을 최대화한다.
* 단점: 끝점(tail) 관리가 중요하며 출구 방향과 충돌하면 병목이 발생한다.
* 추천 조건: 대기 인원이 많고 “대기 구역”을 확보 가능할 때 사용한다.

3. **Parallel Lanes(2열/다열 병렬)을 사용한다**

* 장점: 처리량(throughput)을 올리기 좋다.
* 단점: 합류(merge) 지점 설계가 필수이며 충돌/끼어듦이 발생한다.
* 추천 조건: 서비스 포인트가 2개 이상이거나 입장 게이트가 다수일 때 사용한다.

4. **Overflow Lane Open(오버플로우 레인)을 사용한다**

* 장점: 급격한 피크에서 통로를 지키며 대기를 흡수하는 응급 처치로 유효하다.
* 단점: 개방/폐쇄 타이밍이 중요하며 빈번히 바꾸면 혼란이 발생한다.
* 추천 조건: 시간대별 피크가 반복될 때 사용한다.

5. **Holding Pen(대기 격리 구역)을 사용한다**

* 장점: 통로/비상동선 보전에 가장 강하며 통로로 새는 줄을 격리한다.
* 단점: 체감 대기가 길어 보일 수 있어 안내/표지가 필요하다.
* 추천 조건: 통로가 좁거나 비상동선이 인접하거나 인파가 거칠 때 사용한다.

6. **Priority / Appointment Lane(예약/우선 레인)을 사용한다**

* 장점: 예약자/약자/패스트패스 처리로 혼란을 감소시킨다.
* 단점: 정책이 명확해야 하며 현장 갈등이 발생할 수 있다.
* 추천 조건: 예약 기반 체험 또는 검증된 우선권 운영이 있을 때 사용한다.

## 3) 장소 조건(사이즈·인원·입출구)에 따라 패턴을 결정하는 로직을 정의한다

### 3-1. 입력 파라미터를 정의한다

* **공간 기하(geometry)를 측정한다**

  * 통로 폭(주 통로/보조 통로)을 측정한다.
  * 대기 구역 면적(줄 전용 구역)을 산정한다.
  * 비상동선/출구 위치와 buffer 구역(절대 침범 금지 구역)을 확정한다.
  * 기둥/벽/전시물 등 고정 장애물을 반영한다.
* **운영 파라미터를 정의한다**

  * 서비스 포인트 수를 정의한다.
  * 처리율(μ)을 1분당 처리 인원으로 측정한다.
  * 피크 도착률(λ)을 시간대별 유입 증가로 추정한다.
* **입·출구 구조를 정의한다**

  * 입구 수(단일/다중)를 정의한다.
  * 출구 구조(입출 동일/분리형)를 정의한다.
  * 동선이 교차하는지 여부를 판단한다.

### 3-2. 줄 패턴 선택 규칙을 정의한다

* **Rule 1**: egress buffer에 근접하면 “Holding Pen / Straight” 위주로 선택한다.
* **Rule 2**: 대기 면적이 좁고 인원이 많으면 “Serpentine”을 선택한다.
* **Rule 3**: 서비스 포인트가 2개 이상이면 “Parallel + merge 설계”를 적용한다.
* **Rule 4**: 피크가 짧고 급격하면 “Overflow Lane”을 개방/폐쇄한다.
* **Rule 5**: 입구가 2개 이상이면 “입구별 pre-queue + 합류” 또는 “입구별 독립 큐”를 적용한다.
* **Rule 6**: 통로 폭이 좁으면 “줄을 통로 밖 격리 구역”에 우선 배치한다.

## 4) 사이즈/인원에 따른 대기 수용량 계획을 수립한다

정확한 값은 행사장 규정과 현장 지침에 따라 달라지며, 설계 관점에서 최소 기준을 수립한다.

### 4-1. 수용량 산식을 정의한다

* **대기 수용량(capacity)** ≈ (대기 구역 면적) × (허용 밀도)로 근사한다.
* 밀도는 안전을 위해 보수적으로 설정한다.
* QueueFlow의 목표는 “최대 수용”이 아니라 **spillback이 egress를 침범하기 전에 레이아웃을 바꿔 버티는 것**이라 정의한다.

### 4-2. 3단계 운영 기준을 정의한다

* **Green**: 대기 수용 여유 상태로서 기본 패턴을 유지한다.
* **Yellow**: tail이 buffer 근처로 접근하여 serpentine 확장 또는 overflow 준비를 수행한다.
* **Red**: spillback이 발생하여 holding pen 또는 overflow를 즉시 실행하고 로봇/인력을 동원한다.

이 기준은 “사람 수”보다 **tail 위치와 통로 침범 여부**를 기준으로 설정한다.

## 5) 센서 배치 계획을 수립한다

센서 수량보다 **목표 관측값을 안정적으로 만드는 위치**가 중요하다고 정의한다.

### 5-1. 핵심 이벤트 4개를 정의한다

1. Queue tail(줄 꼬리) 위치를 관측한다.
2. Spillback(통로 침범) 여부/깊이를 관측한다.
3. Egress intrusion(비상동선 침범)을 관측한다.
4. Inflow 급증(피크 시작 신호)을 관측한다.

### 5-2. 추천 배치를 정리한다

#### A) Overhead 카메라(또는 고정 시야 카메라)를 배치한다

* 배치 위치를 다음처럼 정의한다.

  * 대기 구역 전체가 보이는 천장/높은 구조물에 설치한다.
  * 최소 1대는 queue tail 구역과 통로 경계선을 포함하도록 설치한다.
* 시야 설계를 다음처럼 정의한다.

  * 서비스 포인트보다 줄 끝의 확산 방향을 우선 관측한다.
  * 통로 경계선을 가로지르는 라인이 화면에 들어오게 구성한다.

#### B) Fixed LiDAR(또는 depth/people-count 센서)를 배치한다

* 배치 목적을 다음처럼 정의한다.

  * 카메라 가림(occlusion)을 보완한다.
  * zone occupancy를 안정적으로 측정한다.
* 배치 위치를 다음처럼 정의한다.

  * 통로/비상동선 경계를 커버하도록 설치한다.
  * 사람 흐름이 교차하는 병목 한 곳을 우선 커버한다.

#### C) 입구/게이트 계측을 선택적으로 배치한다

* 입구가 여러 개면 입구별 inflow를 계측하여 정책 판단을 안정화한다.
* 카메라 추가 또는 라인 크로싱 계측으로도 충분하다.

정리하면 센서 배치의 핵심은 **서비스 포인트가 아니라 tail/egress/통로 경계**를 커버하는 데 있다.

## 6) 입구/출구 구조별 운영 시나리오를 정의한다

### 6-1. 단일 입구·단일 출구(입출 동일) 시나리오를 정의한다

* 가장 흔한 형태로서 부스 체험/팝업에 해당한다고 정의한다.
* **Holding pen 또는 serpentine을 부스 옆 공간에 격리**하고 통로를 보전한다.
* 줄이 통로로 퍼지면 입구/출구 교차로 충돌이 증가한다.
* 피크 전 overflow를 준비하고, 피크 시 holding pen과 안내를 강화한다.

### 6-2. 단일 입구·출구 분리형(일방향 동선) 시나리오를 정의한다

* serpentine과 분리된 exit lane을 확보한다.
* exit 쪽이 막히면 역류(backflow)가 발생한다.
* exit lane을 hard keepout으로 고정하고 tail이 exit 방향으로 튀지 않게 barrier points를 설계한다.

### 6-3. 다중 입구·단일 서비스 포인트 시나리오를 정의한다

* 다음 2가지 중 하나를 선택한다.

  1. 입구별 독립 pre-queue 후 합류 지점 1개로 통제한다.
  2. 주 입구로 유도하고 보조 입구는 overflow 시에만 개방한다.
* 합류 설계가 없으면 끼어들기/충돌이 급증한다.
* 입구별 inflow 측정이 있어야 정책이 흔들리지 않는다.

### 6-4. 다중 서비스 포인트 시나리오를 정의한다

* parallel lanes와 명확한 merge/분기 규칙을 적용한다.
* “한 줄에서 분기”와 “각자 줄” 중 하나로 고정하여 현장 혼란을 방지한다.
* QueueFlow 관점에서 “2열 전환/1열 복귀” playbook이 가장 가치가 크다고 본다.

## 7) 장소 규모에 따른 배리어/포인트 설계 가이드를 정의한다

### 7-1. 작은 공간 가이드를 정의한다

* 통로 침범 0을 최우선 목표로 설정한다.
* holding pen / 직선형 위주 패턴을 사용한다.
* 카메라 1대로 tail과 통로 경계를 커버하면 충분한 경우가 많다.
* 로봇은 자주 움직이지 않고 한 번 전환하면 일정 시간 유지하여 혼란을 최소화한다.

### 7-2. 중간 공간 가이드를 정의한다

* 피크 대응과 레이아웃 전환을 운영 표준으로 만든다.
* serpentine + overflow + parallel 전환 패턴을 사용한다.
* 대기 구역 1 + 통로/egress 1로 최소 2개 시야를 확보한다.
* 시간표 기반(pre-arm) 시나리오가 효과가 크다.

### 7-3. 큰 공간 가이드를 정의한다

* 존 간 spillover를 차단하고 병목이 이동하는 풍선효과를 방지한다.
* 존별 독립 큐 + 중앙 통로 keepout을 적용한다.
* 존 단위 density와 주요 병목 2~3곳을 커버한다.
* 다중 로봇/스케줄링이 필요한 시설 운영 OS에 가까운 형태로 발전한다고 본다.

## 8) 행사 하루 기준 운영 계획을 수립한다

### 8-1. 행사 전(설치/검증) 절차를 정의한다

* 대기 구역/통로/비상동선 선을 확정한다.
* 패턴 3~5개만 승인하여 운영 가능성을 확보한다.
* Red 조건에서 자동 수행 SOP를 확정한다.

### 8-2. 행사 중(실시간) 절차를 정의한다

* 상태를 Green/Yellow/Red로 단순화한다.
* Yellow에서 추천 및 준비를 수행하고 Red에서 승인 후 실행 또는 즉시 복구 playbook을 수행한다.
* 레이아웃을 자주 바꾸지 않으며 전환 쿨다운을 둔다.

### 8-3. 행사 후(리포트/개선) 절차를 정의한다

* spillback 발생 시간대를 기록한다.
* 패턴별 효과(성공률)를 평가한다.
* 인력 개입 지점을 기록한다.
* 다음 행사에서 barrier points/패턴 개선안을 도출한다.

## 9) MVP 범위를 현장 적용 중심으로 좁힌다

처음부터 모든 줄 모양 자동 설계로 접근하면 실패 확률이 크다고 판단한다. MVP 범위를 다음처럼 고정한다.

* 존 1개를 대상으로 한다.
* 패턴 2~3개만 사용한다: `기본(직선/serpentine)` + `overflow` + 필요 시 `holding pen`을 포함한다.
* 센서는 tail/통로/egress만 확실히 관측한다.
* 성공 지표는 spillback 시간 감소, egress 침범 0, 운영자 업무시간 감소로 정의한다.

리포를 코드 기준으로 뜯어보면, **ROS2swarm은 “멀티 로봇 스폰 + 네임스페이스 분리 + 행동 패턴(pattern) + 충돌 회피 보호층(hardware protection)”을 한 묶음으로 만든 ROS 2 swarm 프레임워크**라 정의한다. 그리고 **Gazebo에서 TurtleBot3 4대를 군집처럼 띄우는 것**은 이 저장소의 기본 스크립트가 이미 대부분 수행한다고 판단한다. 다만 중요한 전제로서 **공식 지원 축은 ROS 2 Dashing/Foxy 계열이고, 설치 가이드는 Ubuntu 20.04 + ROS 2 Foxy + Gazebo 11(Gazebo Classic) 기준**임을 확인한다. 반면 TurtleBot3 최신 문서는 Humble/Jazzy에서 `ros_gz` 계열을 안내하므로, **Humble/Jazzy 환경에서는 그대로 적용되지 않고 포팅이 필요할 가능성이 크다**고 판단한다. ([GitHub][1])

## 1) 결론으로서 4대 TurtleBot3 스폰 방식을 정리한다

핵심 진입점은 `start_simulation.sh`라 정의한다. 이 스크립트는 빌드 후 `launch_gazebo/create_enviroment.launch.py`를 실행하면서 기본값으로 다음을 전달한다.

* `gazebo_world:=arena_large.world`
* `pattern:=drive_pattern`
* `number_robots:=4`
* `total_robots:=4`
* `robot:=burger`
* `sensor_type:=lidar`
* `x_start:=0.0`, `x_dist:=0.0`
* `y_start:=0.0`, `y_dist:=1.0`
* `driving_swarm:=False`
* `logging:=True`
* `ROS_DOMAIN_ID=42`

즉, **Burger 4대를 arena_large.world에 띄우고 Y축 1m 간격으로 배치하며 기본 행동을 `drive_pattern`으로 설정한다**고 정리한다. `create_enviroment.launch.py` 내부 루프를 보면 각 로봇을 `robot_0`, `robot_1`, `robot_2`, `robot_3` 네임스페이스로 생성하며 위치를 `(x_start + i*x_dist, y_start + i*y_dist)`로 계산한다. 기본값이면 대략 `(0,0)`, `(0,1)`, `(0,2)`, `(0,3)`에 배치한다고 판단한다. 파일명은 `create_environment`가 아니라 **`create_enviroment.launch.py`**로 오타가 포함되어 있으니 그대로 사용해야 한다고 명시한다. ([GitHub][2])

중요한 점은 **Gazebo 스폰과 실제 주행 시작이 분리되어 있다**고 정의한다. `start_simulation.sh`는 환경과 로봇, 패턴 노드를 띄우지만 로봇이 즉시 움직이지 않는다. 실제 시작은 `start_command.sh`가 `/swarm_command` 토픽에 `communication_interfaces/msg/Int8Message`로 `{data: 1}`을 발행할 때 이루어진다. 이 스크립트는 해당 메시지를 여러 번 반복 발행한다. ([GitHub][3])

## 2) 런치 체인 구조를 정리한다

실행 흐름을 아래처럼 이해한다.

### A. `start_simulation.sh`를 정의한다

이 스크립트는 `colcon build --symlink-install --allow-overriding communication_interfaces launch_gazebo ros2swarm`를 호출하고, `install/setup.bash`를 source한 뒤 `ROS_DOMAIN_ID=42`로 `create_enviroment.launch.py`를 실행한다. 즉, **빌드 + 환경 설정 + 시뮬레이션 런치**를 한 번에 묶는 엔트리 스크립트라 정의한다. ([GitHub][2])

### B. `create_enviroment.launch.py`의 역할을 정리한다

이 런치 파일은 오케스트레이터로 동작하며 다음 네 가지를 수행한다.

1. **Gazebo Classic을 실행한다**
   `start_gazebo.launch.py`를 통해 `gazebo <world> -s libgazebo_ros_factory.so -s libgazebo_ros_init.so`를 실행한다.

2. **ground truth publisher를 실행한다**
   `ground_truth_publisher`가 `/gazebo/model_states`를 받아 `/ground_truth`로 재발행한다.

3. **각 로봇을 스폰한다**
   `number_robots`만큼 루프를 돌며 `add_bot_node`를 실행하고, `robot_i` 네임스페이스와 지정 좌표에 스폰한다.

4. **각 로봇에 패턴 스택을 부착한다**
   로봇마다 `bringup_patterns.launch.py`를 포함하여 센서 레이어, 행동 패턴, 하드웨어 보호층, `robot_state_publisher`를 함께 실행한다.

이 구조 때문에 ROS2swarm은 “Gazebo에서 로봇 여러 대 스폰”을 넘어 **각 로봇마다 독립 스택을 namespaced하게 띄우는 형태**라 정리한다. ([GitHub][4])

## 3) 4대 멀티 로봇에서 토픽/TF 충돌을 방지하는 방식을 정리한다

`add_bot_node.py`는 TurtleBot3의 SDF를 읽어 `/spawn_entity` 서비스로 모델을 Gazebo에 스폰한다. 이후 SDF 내부 diff-drive plugin의 ROS remapping을 수정하여 **`/tf`를 `/<robot_namespace>/tf`로 리맵**하고 spawn request에 `robot_namespace`를 설정한다. 즉, Gazebo 플러그인 레벨에서 TF 충돌을 줄인다고 정리한다. ([GitHub][5])

또한 `bringup_patterns.launch.py`는 `robot_state_publisher`를 로봇 네임스페이스 안에서 실행하고, `/tf`와 `/tf_static`을 네임스페이스 내부 토픽으로 remap한다. 따라서 로봇별 TF 트리가 분리된다고 정리한다. ([GitHub][6])

## 4) 주행 데이터 플로우를 정의한다

이 저장소에서 주행은 다음 파이프라인으로 구성된다고 정의한다.

```text
/robot_i/scan
   -> lidar_layer
   -> /robot_i/range_data

pattern node
   -> /robot_i/drive_command

/robot_i/range_data + /robot_i/drive_command
   -> hardware_protection_layer
   -> /robot_i/cmd_vel
```

`lidar_layer`는 `LaserScan`을 받아 각 beam의 각도와 range를 가진 `RangeData`로 변환하여 `/range_data`에 퍼블리시한다. `MovementPattern` 계열 패턴 노드는 `/drive_command`에 `Twist`를 퍼블리시한다. `hardware_protection_layer`는 패턴 명령과 센서 기반 회피 결과를 합성하거나 대체하여 최종 `/cmd_vel`을 생성한다고 정의한다. ([GitHub][7])

### 시작/정지 게이트로서 `AbstractPattern`을 정의한다

모든 패턴은 `AbstractPattern`을 상속한다. 이 베이스 클래스는 `/swarm_command`를 구독하고 START(=1) 수신 시 `start_flag=True`, STOP(=0) 수신 시 `False`로 설정한다. 그리고 래퍼를 통해 `start_flag`가 켜졌을 때만 동작하도록 제어한다. 따라서 `/swarm_command`가 오기 전까지 주행이 시작되지 않는다고 정의한다. ([GitHub][8])

### 패턴 공통 출력으로서 `MovementPattern`을 정의한다

`MovementPattern`은 패턴별 `/<namespace>/drive_command` 퍼블리셔를 생성한다. 또한 swarm 정지 또는 destroy 시 zero `Twist`를 퍼블리시하여 출력 안정성을 보장한다고 정의한다. ([GitHub][9])

### 센서 레이어로서 `lidar_layer`를 정의한다

`lidar_layer.py`는 `LaserScan`에서 `angle_min + i*angle_increment`로 각도를 재구성하고 `ranges`와 `angles`를 묶어 `RangeData`로 변환한다. 패턴/보호층은 raw `LaserScan` 대신 정규화된 `RangeData`를 사용한다고 정의한다. ([GitHub][7])

### 최종 제어로서 `hardware_protection_layer`를 정의한다

이 노드는 `drive_command`와 `range_data`를 받아 장애물 회피가 필요하면 패턴 `Twist` 대신 회피 `Twist`를 사용하고, 그렇지 않으면 패턴 명령을 그대로 `/cmd_vel`로 보낸다. 내부적으로 `ScanCalculationFunctions.potential_field(...)`를 호출하여 장애물 벡터를 계산한다고 정의한다. 따라서 실제 로봇이 받는 명령은 패턴 출력이 아니라 보호층을 통과한 결과라 정의한다. ([GitHub][10])

## 5) 기본 4대 실행에서 `drive_pattern`의 의미를 정의한다

기본 `pattern:=drive_pattern`은 swarm intelligence라기보다 **모든 로봇에 동일 속도 명령을 주는 baseline**이라 정의한다. `drive_pattern.py`는 주기 타이머로 `Twist.linear.x = drive_linear`, `Twist.angular.z = drive_angular`를 `/drive_command`에 퍼블리시한다. Burger 기본 YAML은 다음 값을 사용한다.

* `drive_timer_period: 0.25`
* `drive_linear: 0.22`
* `drive_angular: 0.0`

따라서 기본 설정에서는 4대 모두 0.25초마다 0.22 m/s 직진 명령을 낸다고 정리한다. 다만 장애물이 가까우면 `hardware_protection_layer`가 회피 명령으로 덮어쓴다. Burger 보호층 기본값은 `min_range: 0.12`, `max_range: 0.300`, `threshold: 5`, `max_translational_velocity: 0.22`, `max_rotational_velocity: 2.84`라 정리한다. 따라서 30 cm 안쪽으로 접근하면 실제 `/cmd_vel`이 달라질 수 있다고 판단한다. ([GitHub][11])

## 6) swarm-like 동작을 제공하는 패턴을 정리한다

ROS2swarm은 여러 패턴을 제공하며, TurtleBot3용 movement pattern으로 `drive_pattern`, `dispersion_pattern`, `aggregation_pattern`, `attraction_pattern` 등을 제공한다고 정리한다. `setup.py` 엔트리 포인트와 launch/YAML에서 이를 확인한다. ([GitHub][12])

### `attraction_pattern`을 정의한다

이 패턴은 `range_data`를 받아 물체 방향 벡터를 계산한다. Burger 기본값은 `alone_angular: 1.0`, `alone_linear: 0.0`이므로 탐지 대상이 없으면 제자리 회전하고, 대상이 있으면 해당 방향으로 유도한다고 정리한다. 다만 LiDAR 기반이라 벽과 로봇을 완전히 구분하지 못할 수 있어 벽도 attraction 대상처럼 작용할 수 있다고 판단한다. ([GitHub][13])

### `aggregation_pattern`을 정의한다

이 패턴은 `EXPLORE -> JOIN_GROUP -> STAY_IN_GROUP -> LEAVE_GROUP` 상태 머신을 가진다. LiDAR 객체 분할로 근처 로봇군을 추정하고, 탐색→접근→체류→이탈을 수행한다고 정리한다. 체류 시간은 `2^(len(robots)) * time_scale + base_stay_time` 형태로 그룹이 클수록 길어지는 경향이 있다고 정리한다. 따라서 군집 현상 관찰에는 `drive_pattern`보다 적합하다고 판단한다. ([GitHub][14])

### `dispersion_pattern`을 정의한다

이 패턴은 서로 떨어지게 하는 동작을 수행하며, swarm 형성보다는 충돌 회피/분산 실험에 가깝다고 정리한다. ([GitHub][15])

## 7) Gazebo에서 TurtleBot3 4대를 띄우고 주행시키는 절차를 정리한다

### 7-1. 전제 환경을 정리한다

공식 설치 가이드는 Ubuntu 20.04 + ROS 2 Foxy + Gazebo 11 기준이라 정리한다. 또한 `gazebo_ros_pkgs`, `nav2`, `turtlebot3`, `turtlebot3_simulations`의 Foxy 브랜치를 맞춰 설치/빌드하도록 안내한다고 정리한다. ([GitHub][16])

```bash
git clone --recurse-submodules https://github.com/ROS2swarm/ROS2swarm.git
cd ROS2swarm
colcon build --symlink-install
source install/setup.bash
```

이 저장소는 TurtleBot3 모델 SDF를 직접 읽어오므로 `turtlebot3_gazebo`가 설치되어 있어야 한다고 정리한다. ([GitHub][5])

### 7-2. 시뮬레이션을 띄운다

```bash
cd ~/ROS2swarm
bash start_simulation.sh
```

### 7-3. 주행을 시작한다

```bash
cd ~/ROS2swarm
source install/setup.bash
bash start_command.sh
```

또는 아래처럼 한 번만 퍼블리시한다.

```bash
ROS_DOMAIN_ID=42 ros2 topic pub --once /swarm_command \
  communication_interfaces/msg/Int8Message "{data: 1}"
```

### 7-4. 토픽을 확인한다

```bash
ROS_DOMAIN_ID=42 ros2 topic list | grep robot_
```

각 로봇에서 `/scan`, `/range_data`, `/drive_command`, `/cmd_vel`을 확인한다고 정리한다. ([GitHub][7])

## 8) 4대 군집을 제대로 보려면 패턴을 교체한다

기본 패턴이 `drive_pattern`이면 4대가 동일 속도로 이동하는 경향이 있으므로, 상호작용 기반 군집 행동을 보려면 패턴을 바꾸는 것이 맞다고 정리한다.

```bash
pattern:=aggregation_pattern
```

또는

```bash
pattern:=attraction_pattern
```

* `ros2swarm/ros2swarm/movement_pattern/basic/movement_pattern.py`로 공통 퍼블리셔를 제공한다. ([GitHub][9])

### 패턴 계층을 정리한다

* `drive_pattern.py` / YAML로 고정 속도 주행을 수행한다. ([GitHub][11])
* `attraction_pattern.py` / YAML로 유도 동작을 수행한다. ([GitHub][13])
* `aggregation_pattern.py` / YAML로 군집 형성을 수행한다. ([GitHub][14])
* `dispersion_pattern.py` / YAML로 분산 동작을 수행한다. ([GitHub][15])

### 계산 유틸을 정리한다

## 10) 흔한 실패 포인트를 정리한다

### Gazebo는 떴는데 로봇이 안 움직이는 경우를 정리한다

`/swarm_command`를 보내지 않았을 가능성이 높다고 판단한다.

### 다른 터미널에서 토픽이 안 보이는 경우를 정리한다

`ROS_DOMAIN_ID=42`를 동일하게 맞춰야 한다고 정리한다.

### 로봇 스폰 실패를 정리한다

`add_bot_node.py`가 SDF 경로를 직접 참조하므로 `turtlebot3_gazebo` 설치/경로 불일치 시 실패할 수 있다고 정리한다.

### Humble/Jazzy에서 그대로 안 되는 경우를 정리한다

ROS2swarm이 Gazebo Classic 실행부를 사용하며, 가이드가 Foxy/Gazebo11 기준이므로 Humble/Jazzy에서는 포팅이 필요하다고 정리한다.
